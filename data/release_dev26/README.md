## 原因と修正

1. 通常投稿に再送識別子がなかった → 不変のリクエストUUIDとサーバー受付記録を追加。同じUUID・同じ内容は同じ投稿IDと実付与額を返す。内容変更は拒否。投稿削除後も同じリクエストで再生成しない。受付記録は本文/GPSを保持せず内容ハッシュのみ。
2. 投稿成功後の画像失敗でファイルを破棄していた → IndexedDBへ送信前に保存。投稿結果、画像結果を分けてチェックポイントを保持し、成功済みの工程を繰り返さない。完了後だけ端末の再送データを消去。新規投稿は未完了1件を解決してから。
3. AEDのinsertエラー時に写真を削除していた → 固定投稿UUIDで既存結果を照合。結果不明の画像は削除しない。Storageの同じ固定パスへの409は再送として扱い、上書きしない。
4. 非公開画像prepare/finalizeが非冪等で、失敗時に削除申請していた → prepareの同一キー再利用、finalizeの同一画像メタデータ再送を許可。結果不明で削除しない。明示同意した元画像も同じ端末再送機構へ接続。削除済みの同一画像リクエストを再作成しない。
5. GPS待ち中にカメラを閉じても遅れて地図へ遷移する経路 → コールバックの有効性をGPS完了後にも確認。元画像保存後の遅い応答も別撮影画面へ反映しない。
6. 画面が常に+10ptと表示 → RPCが台帳から返した付与額を表示。通常投稿上限のロックを付与関数内にも明示。**旧実装も退会保護トリガーが同じユーザーの書込みを直列化しており、上限超過の発生を実証したものではない。**
7. 利用停止中の画像確定・Storage新規保存と停止管理者判定を補強。
8. 30日保全が旧期限+30日になっていた → 判断日から30日。判断待ち7日はワーカー起動時ではなく保全満了時から数える。
9. Storage一覧のnull応答を削除成功とみなす経路 → 確実な配列応答と対象不在を必須にする。削除試行100回超でDB制約エラーになる経路を修正。throttle時はprocessingと返す。
10. 退会処理がカメラ追加前のテーブルしか消去していなかった → Storage消去確認後にカメラ参照・ハッシュ・寸法・保全理由・監査actorを消去。通常の画像削除でも監査actorを消す。再送IDの不透明な墓標は再作成防止用に保持し、退会処理対象行では消去。
11. プライバシー説明と実機能の不整合 → 非公開加工画像、任意元画像、車載位置記録、端末再送、削除実行の遅延、現行退会手続きを追記。法的適合性の最終審査を実施した意味ではない。

## 検証方法と安全範囲

- DB試験はBEGIN/ROLLBACK。ランダムUUIDのテスト用Auth行・プロフィール・画像メタデータをトランザクション内だけで作成。実ユーザーのAuth削除やStorage APIによる画像削除は行わない。
- 期限はテスト行の日付だけ変更。本番時計を変更しない。期限遷移の共通RPCは同一トランザクション内で動かし、全変更をROLLBACK。
- 画像メタデータを置くSQL試験は実オブジェクト削除のE2Eではない。Storageはモック故障試験で別に確認。
- リクエスト並行性はWeb Locks/同期ガード/DBロック・一意制約を確認。複数の実HTTP接続による並行ストレス試験は未実施。
- ブラウザー描画テスト `tests/aed_review.test.cjs` はChromium未配置で実行不可。ブラウザー取得もタイムアウト。Node上のDOM/VM試験とiPhone実機を混同しない。
- 実運用の管理者パスワードでの成功E2Eは未実施。SQLは権限ロール境界、無効パスワードの拒否、既存の管理内部処理を別々に試験した。

## 追加対応：AED再審査・返答から7日で整理（2026-09-16）

### 仕様・適用範囲

- 否認/rejected・要修正/needs_changesに「再審査を申し込む」を表示。同じ投稿ID・写真を使い、10〜1,000文字の理由・補足で申請する。新しい写真の提出は新規投稿から行う。
- 運営が活動履歴に返答を掲載したサーバー時刻から7日（168時間）で受付終了。既読時刻起算ではない。期限と削除対象を画面・ガイド・プライバシーに表示。
- 申込中は削除対象から除外。再度の返答で新たな7日を設定。複数回の再申込は可能だが、同時に1件、申立て全体で1人24時間あたり3件まで。
- 制度導入前の返答へ期限をバックフィルしない。初回適用時点の期限設定済み・削除対象・削除開始はいずれも0件。実ユーザーの投稿・写真は試験削除していない。
- 承認済み、審査待ち、再審査処理中、申込確認中、退会処理中を保護。承認済みAEDの施設情報・付与ポイントは変更しない。通常の審査画面から直接回答した場合も未処理の申込を回答済みにする。
- 写真をStorage APIで削除→一覧で消去確認→DBでもStorageメタデータ不存在を確認→投稿・申立て・画像審査情報を消去する。削除ID/日時と最小限の操作記録だけを保持し、古いUUIDの投稿や画像再アップロードを拒否する。
